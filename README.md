<summary><b>Задание 1. Резервное копирование.</b></summary>
### Кейс
Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования. 

Необходимо описать, какие варианты резервного копирования подходят в случаях: 

1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.

1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

1.3.* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.

*Приведите ответ в свободной форме.*

---

### ОТВЕТ:


### 1.1. Восстановление данных в полном объёме за предыдущий день
*   **Решение:** Полноразмерное резервное копирование (Full Backup).
*   **Описание:** Для выполнения этой задачи подходит классический **логический бэкап** (дамп всей базы данных через `pg_dump` / `mysqldump`) или **физический бэкап** (копирование бинарных файлов данных). Скрипт запускается по расписанию каждую ночь в период наименьшей активности пользователей. В случае аварии база данных восстанавливается из ночного архива на состояние «на конец вчерашнего дня». 

### 1.2. Восстановление данных за час до предполагаемой поломки
*   **Решение:** Инкрементное/Дифференциальное копирование или технология PITR (Point-in-Time Recovery).
*   **Описание:** Делать полный дамп базы данных каждый час технически невозможно (это создаст критическую нагрузку на диски и заблокирует транзакции). Поэтому применяется комбинация:
    1. Один раз в сутки делается полный бэкап (Full Backup).
    2. Каждый час (или непрерывно) на резервный сервер копируются только **изменения**, произошедшие с момента последнего полного бэкапа. В PostgreSQL это реализуется через архивацию **WAL-логов (Write-Ahead Logs)**, а в MySQL — через **Binary Logs (binlog)**. При аварии восстанавливается ночной бэкап, а затем на него поочередно накатываются часовые логи изменений.

### 1.3.* Моментальное переключение на работающую базу данных (High Availability)
*   **Ответ:** Да, такой кейс возможен и является стандартом для финансовых организаций.
*   **Описание:** Это реализуется с помощью **горячей репликации (Hot Standby)** и утилит автоматического переключения (**Failover**), таких как *Patroni*, *Repmgr* (для PostgreSQL) или *Orchestrator* (для MySQL). В системе постоянно работают два сервера: `Master` (принимает трафик) и `Replica` (синхронно повторяет все изменения). Между ними работает демон отслеживания (Heartbeat). Если `Master` мгновенно сгорает, система мониторинга фиксирует это за 1–3 секунды и автоматически перенаправляет трафик приложения на реплику, делая её новым мастером. Пользователи даже не замечают сбоя.

2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).

2.1.* Возможно ли автоматизировать этот процесс? Если да, то как?

*Приведите ответ в свободной форме.*

---
### ОТВЕТ:
### 2.1. Примеры команд резервирования и восстановления (pg_dump / pg_restore)

Согласно официальной документации PostgreSQL, для создания резервной копии отдельной базы данных в кастомном (сжатом) формате используется утилита `pg_dump`, а для её восстановления — `pg_restore`.

*   **Команда создания резервной копии (Дамп):**
    ```bash
    pg_dump -h localhost -p 5432 -U admin -F c -b -v -f "/backups/catalog_db_backup.dump" catalog_db
    ```
    *Разбор флагов:*
    *   `-h` / `-p` / `-U` — хост, порт и имя пользователя.
    *   `-F c` — формат вывода (Custom). Создает сжатый бинарный архив, который весит меньше всего и поддерживает параллельное восстановление.
    *   `-b` — включать в дамп большие объекты (Blobs).
    *   `-v` — подробный вывод логов работы (Verbose).
    *   `-f` — путь, куда сохранить итоговый файл.
    *   `catalog_db` — имя целевой базы данных.

*   **Команда восстановления базы данных из дампа:**
    ```bash
    pg_restore -h localhost -p 5432 -U admin -d catalog_db -v "/backups/catalog_db_backup.dump"
    ```
    *Разбор флагов:*
    *   `-d catalog_db` — имя базы данных, в которую будут развернуты данные (база должна быть предварительно создана в СУБД как пустая).

### 2.1.* Автоматизация процесса бэкапов в PostgreSQL
Процесс бэкапов автоматизируется с помощью планировщика задач **Cron** и Bash-скриптов.

1. **Создается Bash-скрипт (например, `backup.sh`):**
   ```bash
   #!/bin/bash
   export PGPASSWORD="my_super_secret_password_2026"
   BACKUP_DIR="/var/backups/postgres"
   DATA_TAIL=$(date +%Y-%m-%d_%H-%M-%S)
   
   # Создаем сжатый дамп
   pg_dump -h localhost -U admin -F c -f "$BACKUP_DIR/catalog_$DATA_TAIL.dump" catalog_db
   
   # Удаляем бэкапы старше 7 дней, чтобы не переполнять диск (ротация)
   find $BACKUP_DIR -type f -mtime +7 -name "*.dump" -exec rm {} \;
   ```
2. **Скрипт добавляется в планировщик Cron (`crontab -e`):**
   ```text
   # Запускать скрипт бэкапа каждый день в 02:00 ночи
   0 2 * * * /bin/bash /home/user/scripts/backup.sh
   ```

3.1.* В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?

*Приведите ответ в свободной форме.*
---
### ОТВЕТ:
### 3.1. Пример команды инкрементного резервного копирования MySQL

В СУБД MySQL инкрементное резервное копирование (запись только измененных данных) реализуется через копирование **бинарных логов (Binary Logs)**, либо с помощью профессиональной официальной утилиты **MySQL Enterprise Backup** (или её бесплатного аналога **Percona XtraBackup**).

*   **Вариант 1. С помощью Percona XtraBackup (Низкоуровневый физический инкремент):**
    ```bash
    # 1. Сначала создается базовый полный бэкап:
    xtrabackup --backup --target-dir=/data/backups/base

    # 2. На следующий день создается инкрементный бэкап (записывает только то, что изменилось с момента базового):
    xtrabackup --backup --target-dir=/data/backups/inc1 --incremental-basedir=/data/backups/base
    ```

*   **Вариант 2. С помощью утилиты `mysqladmin` (Переключение binlog-файлов):**
    Если используется стандартный `mysqldump`, для фиксации инкремента (изменений за час/день) принудительно закрывают текущий бинарный лог и открывают новый. Все изменения с этого момента пишутся в свежий файл:
    ```bash
    mysqladmin -u admin -p flush-logs
    ```
    После этого файлы старых бинарных логов (`mysql-bin.00000X`) копируются в безопасное архивное хранилище. Это и есть инкрементный бэкап.

### 3.1.* Преимущества использования реплики перед обычным бэкапом

Обычный бэкап (дамп) — это снимок данных в прошлом, а реплика — это копия базы данных в настоящем времени. Использование реплики дает следующие фундаментальные преимущества:

1.  **Нулевое время простоя при аварии (RTO $\approx$ 0):** Если основной сервер падает, восстановление терабайтной базы из обычного бэкапа может занять долгие часы (пока файлы скачаются и развернутся). Реплика же находится в рабочем состоянии прямо сейчас — переключение на неё занимает пару секунд.
2.  **Отсутствие нагрузки на боевой сервер (Production):** Снятие бэкапа грузит процессор и жесткие диски, что замедляет работу сайта для пользователей. Мы можем подключить утилиту бэкапа к `Slave`-реплике. Основной `Master`-сервер при этом вообще не заметит нагрузки.
3.  **Защита от потери данных за день (RPO $\approx$ 0):** Если бэкап делается раз в сутки (ночью), а сервер упал вечером — вы безвозвратно теряете данные за все дневные часы. Реплика получает изменения асинхронно или синхронно в режиме реального времени, минимизируя потерю данных до долей секунды.
